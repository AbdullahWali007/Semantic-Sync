Overview

Project Introduction

Semantic Sync is a production‑grade, event‑driven pipeline that consumes Debezium CDC events from Apache Kafka, evaluates the semantic drift between the “before” and “after” states, and conditionally synchronises the vector database only when the change is meaningful.

⛔ The Problem We Set Out to Solve

Modern data architectures increasingly rely on Change Data Capture (CDC) to stream real‑time database mutations to downstream systems. One critical downstream system is a Vector Database (e.g., Qdrant, Pinecone), used to power semantic search, recommendation engines, and RAG pipelines.

In a typical deployment, every INSERT, UPDATE, or DELETE on a source table triggers an immediate update to the vector index. This “fire‑and‑forget” approach has several hidden costs:

  • Noise — Many updates are trivial (whitespace, typo fixes, rephrasing) and don't change the underlying meaning.
  • Context Window Overload — Large payloads can overflow LLM context windows.
  • Human Oversight — High‑risk changes (legal clauses, financial figures) require explicit approval.
  • No Semantic Awareness — The pipeline cannot distinguish cosmetic edits from factual changes.

✨ Our Solution: Semantic Sync

At its core, Semantic Sync uses LangGraph to orchestrate a state machine that:

  1. Routes the event based on operation type (INSERT, UPDATE, DELETE, or large payload).
  2. Evaluates updates with an LLM (via a configurable OpenAI‑compatible model) to decide if the change carries new facts, figures, or logic — or is merely cosmetic.
  3. Human‑in‑the‑Loop (HITL) for high‑risk updates — suspends execution, awaits manual APPROVE or REJECT, and resumes.
  4. Synchronises the vector index only when the change is approved or when no drift is detected (short‑circuit).
  5. Caches evaluation results to avoid repeat LLM calls for identical before/after pairs.

🎯 What Problem Does It Solve?

Semantic Sync bridges the gap between database transactions and semantic search indexes by injecting intelligence into the sync process. It ensures your vector index remains fresh, accurate, and cost‑effective — without flooding it with noise or bypassing critical business approvals.

It’s ideal for any organisation that:

  • Uses a vector database for search/retrieval over frequently updated documents.
  • Wants to avoid unnecessary compute costs from trivial updates.
  • Needs audit‑grade control over changes to sensitive data.
  • Requires a robust, scalable, and maintainable pipeline.

“Semantic Sync is not just a pipeline — it’s a semantic gateway that decides what matters before it reaches your AI infrastructure.”

Guide

Comprehensive Guide

This guide walks you through the entire setup and operation of the Semantic Sync pipeline — from installing dependencies to running the API server, Kafka consumer, and tests.

1. Prerequisites

Before you begin, ensure you have the following installed and accessible:

  • Python 3.10+ (tested on 3.11)
  • PostgreSQL 14+ (for LangGraph checkpoint persistence)
  • Kafka (or Redpanda) — a running broker with a topic for CDC events
  • Qdrant — vector database instance (cloud or local)
  • OpenAI API Key — for LLM and embeddings (or compatible alternative)
  • Git (optional, for cloning)

2. Environment Variables

Create a .env file in the project root (or export them in your shell). The following variables are required:

Variable Description Example
POSTGRES_CHECKPOINT_URL PostgreSQL connection string for LangGraph checkpoints postgresql://user:pass@localhost:5432/semantic_sync
EVALUATOR_MODEL OpenAI model for semantic evaluation gpt-4o-mini
EMBEDDING_MODEL OpenAI embedding model text-embedding-3-small
VECTOR_DB_URL Qdrant endpoint URL http://localhost:6333
VECTOR_DB_API_KEY Qdrant API key (if required) your-api-key
OPENAI_API_KEY OpenAI API key sk-...

Optional variables (with defaults): COLLECTION_NAME, KAFKA_BOOTSTRAP_SERVERS, KAFKA_TOPIC, KAFKA_GROUP_ID, HITL_ENABLED, MAX_CONTEXT_TOKENS, CACHE_TTL_SECONDS, LOG_TEXT_MAX_LENGTH, FALLBACK_ASSUME_DRIFT, LLM_MODEL, LLM_TEMPERATURE, LLM_TIMEOUT_SECONDS, LLM_RETRY_MAX_ATTEMPTS, TOKENIZER_ENCODING.

3. Setup Steps

3.1 Clone the repository

# Clone the repo (or download the source)
git clone <your-repo-url>
cd Semantic-Sync

3.2 Create a virtual environment

python -m venv venv
# On Linux/macOS:
source venv/bin/activate
# On Windows:
venv\Scripts\activate

3.3 Install dependencies

Create a requirements.txt with the following:

fastapi
uvicorn[standard]
langchain-openai
langgraph
qdrant-client
psycopg-pool
confluent-kafka
pydantic
tiktoken
tenacity
pytest
pytest-asyncio
python-dotenv

Then install:

pip install -r requirements.txt

3.4 Prepare PostgreSQL Database

CREATE DATABASE semantic_sync;

The LangGraph checkpoint schema will be auto‑created by the saver when the server starts.

3.5 Prepare Qdrant Collection

If the collection does not exist, Qdrant will auto‑create it on first upsert with the correct vector size. Ensure the collection name matches COLLECTION_NAME.

3.6 Prepare Kafka Topic

kafka-topics --create --bootstrap-server localhost:9092 \
  --topic debezium.public.documents \
  --partitions 3 --replication-factor 1

4. Running the API Server

The FastAPI server provides:

  • Ingestion endpoint POST /api/v1/event — accept CDC events.
  • Resume endpoint POST /api/v1/graph/resume/{thread_id} — for HITL.
  • Health check GET /api/v1/health.

Start the server:

uvicorn api.server:app --host 0.0.0.0 --port 8000 --reload

(Remove --reload in production.)

Test the server:

curl http://localhost:8000/api/v1/health
# Should return {"status":"ok"}

5. Running the Kafka Consumer

The consumer is a standalone worker that reads Debezium messages from Kafka and directly invokes the graph (bypassing the HTTP API for lower latency).

python -m worker.kafka_consumer

It will connect to Kafka, subscribe to the topic, and process each message sequentially. Logs will show offset processing and thread IDs.

⚠️ Important: The consumer uses manual offset commit. If a message fails, it will not commit, so the next restart will reprocess it. Consider sending failed messages to a Dead Letter Queue (DLQ).

6. Running Tests

The test suite uses pytest and mocks external dependencies (LLM, Qdrant, embedding). It runs with an in‑memory checkpointer.

pytest tests/test_pipeline.py -v

All tests should pass. If you get import errors, ensure the project root is in PYTHONPATH.

7. Sending a CDC Event

To test the pipeline end‑to‑end, send a simulated Debezium payload to the ingestion endpoint:

curl -X POST http://localhost:8000/api/v1/event \
  -H "Content-Type: application/json" \
  -d '{
    "op": "u",
    "ts_ms": 1700000000000,
    "before": {"id": "123", "content": "Old price $100", "department": "ENG"},
    "after": {"id": "123", "content": "New price $200", "department": "ENG"}
  }'

You’ll receive a thread_id. Use this to monitor logs, or if HITL is triggered, you must resume the thread.

8. Human‑in‑the‑Loop (HITL) Workflow

When a high‑risk update (e.g., department="LEGAL") with semantic drift is detected, the graph suspends at the human_review_node.

  1. The graph pauses and the thread is stored in PostgreSQL.
  2. An external system (e.g., Slack bot) notifies a human. The interrupt call includes context (document_id, before/after preview, reasoning).
  3. The human decides to APPROVE or REJECT.
  4. The decision is sent via the resume endpoint:
curl -X POST http://localhost:8000/api/v1/graph/resume/doc_123 \
  -H "Content-Type: application/json" \
  -d '{"action": "APPROVE"}'

The graph resumes; if approved, the sync proceeds; if rejected, the sync is skipped.

💡 Note: The thread_id is constructed as doc_{document_id} in the consumer. For server ingestion, a UUID is generated; you can pass a thread_id in the request payload for easier correlation.

9. Monitoring & Logging

  • Logs — All components log to stdout with structured messages including event_id or thread_id. Use LOG_TEXT_MAX_LENGTH to avoid huge logs.
  • Metrics — The system does not include built‑in Prometheus metrics, but you can add them by decorating nodes with counters.
  • Health Checks — The API server has /health. The consumer does not have a health endpoint; use a separate process to check if it’s running.

10. Scaling & Production Considerations

  • API Server — Stateless; run multiple replicas behind a load balancer. The AsyncPostgresSaver uses the same database, so all replicas share state.
  • Kafka Consumer — Scale horizontally by increasing partitions and running multiple consumer instances in the same group.
  • PostgreSQL Pool — Tune max_size according to your concurrency needs (default 10–20).
  • LLM Caching — In‑memory cache is per‑process. For shared caching across instances, replace with Redis.
  • Error Handling — Implement retry with backoff and DLQ for transient failures.
  • Security — Use environment variables or a secrets manager. Never hardcode keys.

11. Troubleshooting Common Issues

IssueSolution
ModuleNotFoundError Ensure all dependencies are installed and PYTHONPATH includes the project root.
OPENAI_API_KEY not set Set the environment variable; the SDK will raise a clear error.
Connection to PostgreSQL fails Check POSTGRES_CHECKPOINT_URL and ensure the database is running.
Kafka consumer unable to connect Verify KAFKA_BOOTSTRAP_SERVERS and network reachability.
Qdrant connection error Check VECTOR_DB_URL and API key; verify the collection exists.
LLM call times out Increase LLM_TIMEOUT_SECONDS or check network/firewall.
HITL interrupt not resuming Ensure you are using the correct thread_id and that the checkpointer has the saved state.

12. Next Steps & Customization

  • Adding new business rules for HITL — Modify evaluator_edge in core/edges.py to check other fields (e.g., amount > 10000).
  • Changing the LLM prompt — Edit core/prompts.py.
  • Integrating with Slack/PagerDuty — In hitl.py, after the interrupt call, add an async webhook to notify humans before suspending.
  • Extending the sync logic — In sync.py, add more metadata to the Qdrant point or handle other databases.
